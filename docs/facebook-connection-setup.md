## Meta Developer steps

1. Open [Wolf CRM Leads](https://developers.facebook.com/apps/1065517586526444/). Add **Create & manage ads with Marketing API** to the existing Leads use case.
2. Open **Facebook Login for Business → Configurations → Create configuration**. Use a **User access token**, with the available user-token lifetime, and include the existing Pages and ad accounts. This implementation validates `debug_token.type == USER`; a system-user token is not interchangeable. Save the configuration ID for the backend.
3. Include these permissions in that configuration: `leads_retrieval`, `pages_show_list`, `pages_read_engagement`, `pages_manage_ads`, `pages_manage_metadata`, `ads_read`, `ads_management`. The login request passes `config_id` and this scope union; Meta permits scope with user-token configurations, although its documentation recommends defining permissions in the configuration. Do not omit them from the configuration.
4. The signing-in person needs appropriate Page and ad-account access (advertising/management), plus Leads Access Manager access if the business customizes lead access. Enable the same existing app for the Page/ad account in the selected portfolio. Page credentials are fetched from authorized Page discovery; they are never used as Ads user credentials.
5. In **Facebook Login for Business → Settings**, retain HTTPS/strict matching and add all three exact redirect URLs below. The canonical connection uses the new URL when configured, and accepts in-flight/legacy callback paths. The `wolfcrm://…` app return is generated by the backend; it is not the Meta OAuth redirect.
6. Configure Page webhooks with the exact callback below, the existing backend verify token, and the **`leadgen`** field. In Wolf CRM select the Page; the existing Leads service subscribes that Page’s `subscribed_apps`. Selecting forms does not replace the app-level webhook verification.
7. Set the deauthorization and data-deletion request URLs below. Existing Leads/Ads callback paths remain supported. On deauthorization Wolf CRM removes credentials and stops both features while retaining company configuration/history. A verified data-deletion request additionally removes Facebook authorization identity and lead integration personal data. Company-owned imported contacts and advertising mutation audit records remain subject to the company’s business-record deletion process; the public confirmation page explains this distinction.
8. For your own business assets, test with an app administrator/developer/tester who also has the asset access. For people/businesses outside the app’s authorized development roles/owned assets, complete the relevant Advanced Access/App Review, business verification and publish requirements shown by Meta. Do not assume development-mode tests prove public onboarding readiness. The current Business Login flow requires all requested permissions to be granted; partial-readiness handling still covers older authorizations, later permission removals and independently unavailable assets.

## Backend variables and secure entry

Use Railway’s authenticated **genuine-grace → production → wolfcrm-backend → Variables** UI during the authorized integration. Enter secrets directly into Railway from the existing Meta app settings/password manager; do not paste them into chat, Git, screenshots or shell commands. Coordinate variable application with the combined backend deployment because Railway variable changes can trigger a deployment. No production variable changes are part of this handoff.

After integration, open **More → Ads → Ads Manager → Connection settings → Connect Facebook**. Sign in once, refresh discovery, select ad accounts and save. In **Ads → Leads**, select Pages/forms, review mappings/defaults and native-vs-Zapier routing before enabling intended imports. Existing native lead IDs remain deduplicated; existing Zapier configuration is untouched. Never enable competing import routes for the same form without reviewing the preserved routing controls.

An old authorization stays usable until deliberately reconnected, expired or revoked. Fresh combined consent is required; the implementation never copies an old token to another app ID. Reconnect retains Page/form/account choices, mappings, imported contacts, saved report views and automations. Review the five separate readiness rows: lead retrieval, subscriptions, processing, Ads reporting, Ads editing. User tokens expire; reconnect when requested. “Pause lead importing” and “Enable Ads operations” are independent; full disconnect removes both services’ stored credentials.
