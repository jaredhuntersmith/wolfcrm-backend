# Editing existing automations and recurring AI work

Use automation_catalog_page with a relevant section and short query; follow next_offset when needed. The legacy automation_catalog tool returns a compact engine overview; use automation_catalog_page for entries. The full native REST catalog remains available to human editors. Read automation_node_schema for each reviewed action/trigger and automation_get/draft for the current graph hash. Use automation_graph_save with that exact hash to add or edit nodes, edges, ports, conditions, waits, branches, loops, notes and safety settings. Inspect the saved graph before publishing with its new hash. Draft save invokes canonical graph validation but does not publish; publication validates the saved graph again. Existing protected credentials remain redacted and unchanged; AI/role permission controls remain human-only. Publishing/resuming/executing recursively checks actual referenced published workflows. Dynamic child IDs require the normal human workflow. New catalog items default unavailable until explicitly reviewed.

Use automation_metadata_save for name/folder/concurrency/reentry/failure settings with record_hash. Use automation_activation_schedule_set with the current automation_get record_hash to set one to 32 activation windows: timezone company or IANA; once windows need at least one offset-aware start_at/end_at, and weekly windows need weekdays Monday=1 through Sunday=7 with HH:mm:ss start_time/end_time. Set schedule to null to clear it. A schedule edit does not publish, resume, or start a run. Use automation_off for an indefinite Off state, automation_pause with a future ISO pause_until for a timed pause, and automation_resume to turn an eligible published graph back On. Applying a draft preserves Off or a timed pause. These controls do not undo work already started. Existing draft cloning, duplicate/archive, run histories, draft dry tests, explicit published manual runs, cancel and recovery all use canonical services. Starting/retrying can execute external effects; exact approval and actual automations.run permission apply. Never claim cancellation undoes a completed effect. Dry tests cannot prove live provider delivery.

A trigger starts a run; its filters and condition nodes select qualifying events. In a stage-entered event, the engine loads the entering Contact as `contact`, even if a later SMS action addresses someone else. To notify a fixed recipient with the entering Contact's name, use a reviewed `pipeline.stage_entered` trigger (no stage filter means any stage) and a connected `sms.send` action with the recipient phone in `phone` and text such as `New stage contact: {{contact.name}}` in `body`. Read both exact node schemas. A separate connected SMS node is required for each additional recipient; each send keeps its own delivery receipt and normal consent/provider/business-hour limits. Do not turn a template variable into a trigger by itself or assume a dry test delivered a message.

For a daily/weekly/monthly AI report, use time.schedule with schedule frequency, time HH:MM, timezone company or IANA; weekdays Monday1–Sunday7 for weekly, month_day for monthly. Default catch-up window15 minutes, configurable1–120. Only published enabled rules run; no backfill before publication. Missing DST wall times or calendar dates skip, repeated wall time fires once. The existing durable scheduler deduplicates automation/node/local date, rechecks pause/version and supports restart recovery. assistant.task binds the published author/current grants, chosen funding/model, bounded steps/cost and explicit allowed tools. It waits durably, saves a configured Note once, or follows the existing error path. Scheduled reports retrieve fresh authorized data, not old chat prose.
